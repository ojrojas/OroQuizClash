# Research: Round Engine

**Feature**: `005-round-engine` | **Date**: 2026-08-27 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

## Summary

0 `NEEDS CLARIFICATION` en spec; investigación consolida 7 decisiones para las 5 invariantes de ronda (RoundNumber/Difficulty/Question/TimeLimit/Status), flujo 8 pasos sobre `Game` aggregate, selección impredecible (`IQuestionSelectionStrategy` ORDER BY NEWID() + PreviousQuestionIds), filtros `Category/Difficulty/Academic/Age` (SPEC-003), progresión `IDifficultyProgressionStrategy` configurable (`Linear` 1→5 default + `Progressive/Adaptive/CategorySpecific`, clamp 1..5), y `rowversion` + `UNIQUE (GameId,RoundNumber)` para concurrencia. Todo alineado a constitución v1.1.0 + BuildingBlocks net10.0 y research de `001/003/004`.

## Decisions

### 1. GameRound como Entity composición con 5 campos invariantes

- **Decision**: `GameRound : Entity<GameRoundId>` con `GameRoundId : StronglyTypedId<Guid>`; campos `GameId : GameId` (FK a Game, cascade), `RoundNumber : int` (1..MaxRounds, único por `GameId`, incremental sin saltos), `Difficulty : DifficultyLevel : Enumeration 1..5` (determinada por `IDifficultyProgressionStrategy`), `QuestionId : QuestionId` (FK lógico a `Question` PUBLISHED, no repetida dentro del mismo `Game`), `TimeLimit : int` (5–300 copiado de `GameConfiguration.TimeLimitPerQuestion` al crear, inmutable), `Status : GameStatus` (5 `ROUND_IN_PROGRESS`, 6 `ROUND_COMPLETED` reusa `GameStatus` values), `StartedAt : DateTimeOffset`, `CompletedAt : DateTimeOffset?`. `Game` expone `IReadOnlyList<GameRound> Rounds { get; }` via private field `_rounds : List<GameRound>` (field access `PropertyAccessMode.Field`), mutación solo vía `Game.StartRound()` (crea) y `Game.CompleteRound(RoundId)` (cambia Status→COMPLETED, set CompletedAt). `RowVersion` permanece en `Game` (no en `GameRound`) + `UNIQUE (GameId,RoundNumber)` para `RoundNumber` sin huecos; `UNIQUE (GameId,QuestionId)` opcional para no repetir pregunta (ya garantizado por `PreviousQuestionIds` check, pero DB constraint extra si se desea).
- **Rationale**: Constitución I (Domain First) exige 5 campos protegidos como invariantes del agregado; `Entity` composición dentro de `Game` garantiza transacción única para `StartRound` (Game + GameRound + Outbox misma `SaveChanges`) y `rowversion` en `Game` protege doble `StartRound` concurrente (segundo → `DbUpdateConcurrencyException` → 409). `RoundNumber` incremental sin saltos necesita `UNIQUE` + `rowversion` (no `IDENTITY` solo).
- **Alternatives**: `GameRound` como `AggregateRoot` separado (rechazado — permitiría dos `ROUND_IN_PROGRESS` simultáneas sin coordinación, rompe invariante; necesitaría saga); `GameRound` como `ValueObject` (rechazado — necesita `RoundId` estable para `SubmitAnswer`/`CompleteRound` y audit); `TimeLimit` recalculado por ronda (rechazado — `GameConfiguration` inmutable tras `StartGame` (SPEC-004), copiar es más simple y auditable).

### 2. Flujo 8 pasos sobre Game aggregate (Round Engine)

- **Decision**: El flujo canónico `StartRound → SelectQuestion → PresentQuestion → WaitForAnswers → EvaluateAnswers → CalculateScores → CompleteRound → IncreaseDifficulty` se orquesta como métodos en `Game` (o `RoundEngine` servicio de dominio si se extrae, pero se adopta sobre `Game` para simplicidad): `StartRound()` crea `GameRound` con `SelectQuestion` (step 2) y asigna `QuestionId`/`Difficulty`/`TimeLimit`/`Status`, `PresentQuestion` es query `GetRoundQuestion` (sin mutación), `WaitForAnswers` es ventana `TimeLimit` donde llegan `SubmitAnswer` (ver `SubmitAnswer.cs` de 004, idempotente), `EvaluateAnswers` compara `AnswerOption.IsCorrect` server-side con `ServerTimestamp - StartedAt ≤ TimeLimit`, `CalculateScores` crea `PointTransaction` ledger (`ANSWER_CORRECT` con `PointsPerRound` ajustado por dificultad si aplica), `CompleteRound()` transita `ROUND_IN_PROGRESS→ROUND_COMPLETED`, `IncreaseDifficulty` no es comando separado sino cálculo `NextDifficulty = IDifficultyProgressionStrategy.NextDifficulty(game, completedRounds)` para la siguiente ronda (prepara `Difficulty` del siguiente `StartRound`). Todos los pasos dentro de una ronda ocurren bajo misma transacción `Game` + `Outbox` en `SaveChanges` (excepto `WaitForAnswers` que es espera externa).
- **Rationale**: Constitución I (Domain First) + V (Authoritative Server Truth) + `Game` como motor (Game lifecycle, Round lifecycle, Question selection, Answer evaluation, Difficulty progression, Score calculation son conceptos de dominio); centralizar en `Game` evita anémico y garantiza `CompleteRound` solo si `EvaluateAnswers` ya ocurrido (aunque `Evaluate` sea en `SubmitAnswer` slice, `Game.CompleteRound` valida que ronda está `IN_PROGRESS` y permite cierre manual o automático por timeout).
- **Alternatives**: `RoundEngine` como servicio de aplicación separado con `Game` anémico (rechazado — expone `_rounds` mutable, viola Domain First); flujo como saga distribuida con RabbitMQ por paso (rechazado — over-engineering para modular monolith, cada paso debe ser transaccional pero no necesita async por ronda).

### 3. Selección impredecible y no repetida (Category/Difficulty/Academic/Age + PreviousQuestionIds)

- **Decision**: `Game.StartRound(IQuestionSelectionStrategy selector, IDifficultyProgressionStrategy difficultyStrategy)` construye `QuestionSelectionCriteria` con `CategoryId = Game.Configuration.CategoryId`, `Difficulty = difficultyStrategy.NextDifficulty(game, completedRounds)` (para el round actual), `AcademicLevel = Category.AcademicLevel` (o `GameConfiguration` AcademicLevel si existe, pero spec dice `GameConfiguration` no tiene AcademicLevel explícito — usa `Category.AcademicLevel` y `Question.AcademicLevel` compatibilidad), `AgeRange = Category.AgeRange`, `PreviousQuestionIds = Rounds.Select(r=>r.QuestionId)`, `GameId`, `RoundNumber = Rounds.Count+1`, `Take=1`. Delega a `selector.SelectAsync(criteria)` donde `selector` es `RandomQuestionSelectionStrategy` (SPEC-003, `ORDER BY NEWID()` / `Guid.NewGuid()` + `Where(!Previous.Contains(Id))` + `Where(Category/Difficulty/Academic/Age ==) + `AsNoTracking` + `Take(1)`). Si `selector` retorna vacío → `Result.Failure(NoAvailableQuestion)` y no crea `ROUND_IN_PROGRESS` (evita fantasma). Impredecible: `Guid.NewGuid()` sin semilla cliente, no correlación por `RoundNumber` o `QuestionId` secuencial, verificado por distribución aleatoria p-value en 1k muestras.
- **Rationale**: Constitución B (no repetition within game + IQuestionSelectionStrategy) + V (Authoritative, impredecible desde cliente) + SPEC-003 FR-004..FR-008 (5 reglas: impredecible, no repetida, Category, Difficulty, Academic/Age). Reutilizar `IQuestionSelectionStrategy` de 003 evita duplicar y mantiene `Specification<Question>` BuildingBlocks.
- **Alternatives**: Selección client-side con lista enviada al cliente (rechazado — viola V, cliente podría predecir o manipular); `Random` con semilla `GameId+RoundNumber` determinista (rechazado — predecible si cliente conoce `GameId`); no excluir `PreviousQuestionIds` (rechazado — viola FR-005, permitiría repetir).

### 4. Filtros Category/Difficulty/Academic/Age y banco agotado

- **Decision**: `QuestionSelectionCriteria` ya incluye `CategoryId` (FK lógico), `Difficulty` (del round, no de `Game.InitialDifficulty` directamente), `AcademicLevel` (string `Category.AcademicLevel.Value`), `AgeRange` (ValueObject con `IsCompatible` overlap `Max ≥ other.Min && Min ≤ other.Max`). `ValidQuestionSpecification` y `QuestionSelectionSpecification` en 003 ya filtran `Status==PUBLISHED` + `AnswerOptions.Count==4` + `ExactlyOneCorrect` + `CategoryId` + `Difficulty` + `AcademicLevel` (case-insensitive `==` ) + `AgeRange` compatibilidad + `!Previous.Contains(Id)`. Si filtros muy restrictivos y banco agotado (ej. 5 preguntas válidas para 5 rondas, pero `Round 6` con `MaxRounds=50` no hay), `StartRound` retorna `NoAvailableQuestion` y permite `Finish` si `completedRounds≥MinRounds` (FR-001) o `ForcedFinish` (SPEC-004).
- **Rationale**: SPEC-003 B + C (AcademicLevel/AgeRange characteristics) + FR-006..FR-008; compatibilidad `AgeRange` como overlap no igualdad exacta (más flexible para categorías con rango amplio).
- **Alternatives**: Filtro `AcademicLevel` como `enum` cerrado (rechazado — spec dice strings controlados 2–100); `AgeRange` igualdad exacta (rechazado — muy restrictivo, no permitiría solapamiento); crear ronda fantasma con `QuestionId = Guid.Empty` si no hay (rechazado — viola FR-002 5 campos).

### 5. Progresión configurable IDifficultyProgressionStrategy (Linear 1→5 default)

- **Decision**: `IDifficultyProgressionStrategy { DifficultyLevel NextDifficulty(Game game, int completedRounds) }` con `int completedRounds = game.Rounds.Count(r=>r.Status==ROUND_COMPLETED)`. Implementaciones: `LinearDifficultyStrategy` (`Next = clamp(InitialDifficulty + completedRounds, 1,5)` → 1→2→3→4→5 para `Initial=1, Min=5`), `ProgressiveDifficultyStrategy` (ej. 1,1,2,3,5 para curva más lenta), `AdaptiveDifficultyStrategy` (basada en desempeño `PointTransaction` ledger si existe, ej. si avg score >80% sube 2, si <30% baja 1), `CategorySpecificDifficultyStrategy` (mapea `CategoryId` a curva). `Game.StartRound` llama `difficultyStrategy.NextDifficulty(this, completedRounds)` para determinar `Difficulty` del nuevo `GameRound` (no muta `GameConfiguration.InitialDifficulty`). Estrategia inyectada via `AddScoped<IDifficultyProgressionStrategy, LinearDifficultyStrategy>` en `Program.cs` (configurable por `appsettings.json` `Game:DifficultyStrategy` o `DifficultyProgressionStrategy` enum). Al menos `Linear` + 2 más registradas (Progressive, Adaptive). Clamp 1..5 si `Linear` pide 6.
- **Rationale**: Constitución C (Difficulty configurable, no hardcode, al menos 5 levels, progression via strategy `Linear/Progressive/Adaptive/CategorySpecific`) + SPEC-005 ejemplo `Round 1→Level1 ... 5→5` + FR-009/010 (intercambiable sin cambiar flujo). `Linear` como default simple para MVP sin over-engineering.
- **Alternatives**: `Difficulty` fija por `Game` (rechazado — viola C, no progresión); `IncreaseDifficulty` como comando separado `POST /rounds/{id}/increase` (rechazado — complica API, es cálculo para siguiente ronda); hardcode `Linear` sin estrategia (rechazado — viola C, requiere ADR para cambiar).

### 6. PresentQuestion filtrado IsCorrect y Wait/Evaluate/Calculate sincrónicos

- **Decision**: `GetRoundQuestionQuery(GameId, RoundId)` → `IRepository<Game,GameId>` rehidrata `Game` con `Include(Rounds)` → encuentra `GameRound` por `RoundId` → carga `Question` via `IRepository<Question,QuestionId>` → mapea a DTO `RoundQuestionResponse` con `QuestionId/Text/CategoryId/Difficulty/TimeLimit/Status/RoundNumber` + `AnswerOptions` donde `IsCorrect` filtrado si `User.IsInRole("PLAYER")` (o `PLAYER` claim) → solo `Id/Text/DisplayOrder`; si `ADMIN/GAME_MANAGER` → incluye `IsCorrect`. `WaitForAnswers` no es comando, es ventana `TimeLimit` donde `SubmitAnswer` llega; `EvaluateAnswers` compara `AnswerOption.IsCorrect` server-side (carga `Question` y busca `a.IsCorrect`), `CalculateScores` crea `PointTransaction` (`Type=ANSWER_CORRECT/ANSWER_INCORRECT`, `Points = PointsPerRound` ajustado por `Difficulty` si `ScoringSystem` lo define). `SubmitAnswer` ya existe en 004 con idempotencia `IdempotencyKey` (`PlayerId+RoundId`) + `ServerTimestamp - StartedAt ≤ TimeLimit` check; este SPEC lo reutiliza sin duplicar. `PresentQuestion` no revela `IsCorrect` a `PLAYER` pero `GET /api/questions/{id}` (SPEC-003, `ADMIN`) sí expone (no es parte de este SPEC).
- **Rationale**: Constitución V (Authoritative, no trusting cliente `IsCorrect`, remaining time), H (JWT `roles` para filtrado), I (Validation 3 niveles). `PresentQuestion` es query, no mutación, por lo que no necesita `RowVersion`.
- **Alternatives**: Enviar `IsCorrect` a `PLAYER` y confiar en cliente para no mostrar (rechazado — viola V, cliente puede inspeccionar payload); `PresentQuestion` como evento SignalR push (posible, pero `GET` es suficiente para MVP, SignalR opcional futuro).

### 7. Persistencia, concurrencia e idempotencia para 5 campos y 8 pasos

- **Decision**: `OroQuizClashDbContext : AppDbContextBase` ya con `DbSet<Game>`; `GameTypeConfiguration` ya con `HasMany(g=>g.Rounds).WithOne().HasForeignKey("GameId")` (field `_rounds`) + `Property(RowVersion).IsRowVersion()`; `GameRoundTypeConfiguration` con `HasKey(Id→Guid)`, `Property(GameId).HasConversion`, `Property(RoundNumber).IsRequired()`, `Property(QuestionId).HasConversion`, `Property(Difficulty).HasConversion(d=>d.Id, id=>DifficultyLevel.FromId(id))`, `Property(TimeLimit).IsRequired()`, `Property(Status).HasConversion`, `HasIndex(GameId,RoundNumber).IsUnique()` (sin huecos) + `HasIndex(GameId,QuestionId).IsUnique()` opcional (no repetida), `HasIndex(QuestionId)`. `Specification<Game>` para `GetGame` con `Include(Rounds)` + `Include(Players)` + `ApplyAsNoTracking` para lectura; `Specification<GameRound>` no necesario separado (acceso vía `Game`). Transacciones protegen `Game` + `GameRound` + `Outbox` en `SaveChanges` (mismo `DbContext` transaction). `rowversion` en `Game` protege `StartRound`/`CompleteRound` concurrente → `DbUpdateConcurrencyException` → `409 Conflict`. `Idempotency` para `SubmitAnswer` ya en 004 (`IdempotencyKey`), para `StartRound` por `UNIQUE (GameId,RoundNumber)`.
- **Rationale**: Constitución E (SQL Server `rowversion` + filtered indexes, `AppDbContextBase`+Outbox misma transacción, `Specification` con `Include`), F (optimistic concurrency preferido, at-least-once idempotency). `UNIQUE` + `rowversion` evita `RoundNumber` duplicado por concurrencia.
- **Alternatives**: `GameRound` como `DbSet` separado con FK físico cross-aggregate (rechazado — `GameRound` es `Entity` composición, no agregado separado, transacción única más simple); `RowVersion` en `GameRound` también (innecesario — `Game` es agregado raíz, su `RowVersion` protege todo); no usar `UNIQUE` (rechazado — permitiría huecos/duplicados por concurrencia).

## Resolved Clarifications

| Topic | Resolution |
|-------|------------|
| IncreaseDifficulty como endpoint separado | No es endpoint; es cálculo `NextDifficulty` para siguiente ronda dentro de `StartRound` siguiente. Se documenta en Assumptions y no se expone `POST /rounds/{id}/increase-difficulty`. |
| TimeLimit por ronda vs global | `GameRound.TimeLimit` copia `GameConfiguration.TimeLimitPerQuestion` al crear; inmutable tras creación, no se recalcula entre rondas. |
| PresentQuestion filtrado por rol | `PLAYER` ve DTO sin `IsCorrect`, `ADMIN/GAME_MANAGER` puede ver vía `GET /api/questions/{id}` (SPEC-003). Se deja como guarda en `GetRoundQuestion` handler con `User.IsInRole`. |
| Banco agotado para siguiente ronda | `StartRound` retorna `NoAvailableQuestion` (409) y no crea ronda; `Finish` permitido si `completed≥MinRounds` (FR-001), `ForcedFinish` si no. |
| Estrategia default si no se especifica | `Linear` (1→2→3→4→5 clamp 1..5) si `DifficultyStrategy` no se especifica o es null en `GameConfiguration`. |
